# Family Backend Alignment and Performance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Align the Family setup, checkout, management, permissions, calendar, meals, subscription operations, localization, and error handling with the backend reference while reducing unnecessary rebuilds and removing only verified unused code.

**Architecture:** Preserve the existing feature-first Flutter architecture. Keep Family setup/checkout in their current features, keep Family management and member meal flows in `subscription_settings`, and keep the generic subscription calendar independent unless an audited shared contract requires a compatible model change. Route all user-facing text through `lib/core/l10n`, and route API error codes and presentation through `lib/core/errors`.

**Tech Stack:** Flutter/Dart, existing Bloc/Cubit-style managers, Retrofit/Dio API services already used by the project, generated JSON serialization, existing theme/style/spacing tokens, and the repository's current test/analyzer tooling.

## Global Constraints

- Read and follow `rules/ui_rules.md` before every UI change.
- Do not redesign the supplied Family UI; Figma/design evidence remains the visual source of truth.
- Do not hardcode user-facing strings, colors, spacing, dimensions, asset paths, enum labels, or error copy.
- Use `lib/core/l10n` for every new or changed user-facing string and support every configured locale.
- Use `lib/core/errors` for error types, backend code mapping, localized presentation, and error widgets.
- Preserve backend enum names and camelCase request fields; do not translate protocol values.
- Use server IDs, `subscriptionId`, `batchId`, `batchVersion`, capabilities, and expected versions supplied by the API.
- Never activate service locally after payment; re-read server state after WebView/callback/app resume.
- Do not delete a file until imports, routes, DI registration, generated references, and runtime entry points prove it unused.
- Do not add packages, a second state-management approach, or a new architecture.
- Use the existing `flutter_animate: ^4.5.2` package for widget entrance/state animations where the supplied Family design requires motion; do not introduce another animation package or animate every rebuild.
- Keep changes limited to Family-related code, shared l10n/errors required by that work, and verified dead code.
